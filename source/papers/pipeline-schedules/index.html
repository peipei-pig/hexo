三种流水调度

PP=4、m=8、v=2（Interleaved）；三种方案按相同计算量和时间尺度比较。

  • GPipe 先完成这一轮的所有前向，再开始反向。
  • 普通 1F1B 在预热后交替执行前向和反向，更早释放已用完的前向状态。
  • Interleaved 1F1B 让每张 GPU 执行两个 Model Chunk，用更短的计算块填充流水线。

普通 1F1B 没有缩短 Bubble

假设各 Stage 的计算均衡，忽略通信耗时。设 p 为 Stage 数，m 为本轮 Microbatch 数。每个 Stage 做一次前向花 tf，做一次反向花 tb。

  1. 整轮前向。第一份 Microbatch 依次经过 p 个 Stage，需要 p · tf。在此期间，后续 Microbatch 已在其他 GPU 上并行执行。第一份完成时，第二份只剩最后一个 Stage，因此再过 tf 就能完成。之后每隔 tf 完成一份，剩余的 m − 1 份共需要 (m − 1) · tf。整轮前向耗时为 (m + p − 1) · tf。以本例的一次前向为一格，m0 在第 4 格结束时完成，m1 在第 5 格结束时完成，最后一份 m7 在第 11 格结束时完成。
  2. 整轮反向。GPipe 在全部前向完成后开始反向。第一份 Microbatch 沿相反方向依次经过 p 个 Stage，需要 p · tb。随后每隔 tb 完成一份，剩余的 m − 1 份共需要 (m − 1) · tb。整轮反向耗时为 (m + p − 1) · tb。
  3. 单卡空闲时间。整轮耗时等于前向和反向耗时之和。每张 GPU 对 m 份 Microbatch 各执行一次前向和一次反向，忙碌时间为 m · (tf + tb)。整轮耗时减去忙碌时间，就是这张 GPU 的空闲时间。
Ttotal = (m + p − 1) · (tf + tb)
Tideal = m · (tf + tb)
Tbubble = Ttotal − Tideal = (p − 1) · (tf + tb)

用空闲时间除以整轮耗时，分子分母的 (tf + tb) 可以约掉。代入 p=4、m=8、tf=1、tb=2，整轮耗时 33，单卡忙碌 24，空闲 9。

Bubble / 总耗时 = (p − 1) / (m + p − 1) = 9 / 33 ≈ 27.27%
Bubble / 有效计算 = (p − 1) / m = 9 / 24 = 37.5%
前者是交互显示的空闲占比，后者是论文采用的归一化开销。

Activation：从存活份数到可比较的存储当量

0.50A当前 Interleaved 峰值：5.50A

固定 A 为普通完整 Stage 的单份存储量；C1 = (1 − α)A。该参数是教学假设，不表示层数均分就必然得到等分的实际 Activation 字节数。

单看「Microbatch × Chunk」会把 Interleaved 的两个半 Stage 状态误当成完整 Stage。GPU 0 在本文模拟中的原始峰值为 11 个 Chunk 状态；当 C0、C1 的每份状态各为 0.5A 时，可比的峰值是 5.5A，不是 11A。权重 α 用于观察两段层组的 Activation 大小不同时，峰值如何变化。

Interleaved 缩短 Bubble

每张 GPU 执行两个 Chunk

取 v=2，把整个模型按层顺序分成八个逻辑 Stage，仍由四张 GPU 执行。GPU 0 承担 S0 和 S4，GPU 1 承担 S1 和 S5，依此类推。切分均衡时，每个 Chunk 的计算时间约为原物理 Stage 的一半。

m0 先走完 S0 到 S3，再从 GPU 3 回到 GPU 0 进行 S4，最后走到 S7。反向按相反的顺序传递梯度。上方交互中的行始终对应物理 GPU，格子里的 C0、C1 表示这一时段执行的是哪个 Chunk。

每张 GPU 的有效计算时间保持为 m·(t_f+t_b)=24。原来填充和排空的空闲长度合计为 (p−1)·(t_f+t_b)=9；现在每个 Chunk 的 F/B 时长各缩小到原来的 1/v，按论文中的分组交错调度，理想空闲时间变为 9/v=4.5。

Tideal = m · (tf + tb) = 8 × 3 = 24
Tbubble,int = [(p − 1) / v] · (tf + tb) = 3 / 2 × 3 = 4.5
Ttotal,int = Tideal + Tbubble,int = 24 + 4.5 = 28.5
Bubble / 有效计算 = (p − 1) / (m v) = 4.5 / 24 = 18.75%
Bubble / 总耗时 = (p − 1) / (m v + p − 1) = 4.5 / 28.5 ≈ 15.79%
t_f=1、t_b=2，p=4、m=8、v=2。只适用于均衡 Chunk、符合该交错调度的 Microbatch 分组、忽略通信和其他等待的理想情形；不是实测加速比。

通信开销：每个方向从 3 次传递增加到 7 次

普通 PP=4 中，每份 Microbatch 的前向沿 GPU 0 → 1 → 2 → 3 传递 3 次，反向沿原路返回。Interleaved v=2 让前向走完两次这条链，再加一次连接两段的 GPU 3 → 0，合计 7 次。反向同样传递 7 次。

每个方向，每份 Microbatch普通 1F1BInterleaved，v=2
原来的三对相邻 GPU每对 1 次每对 2 次
连接两个 Chunk 的边界0 次1 次
整个 Pipeline 的传递次数3 次7 次

在同一方向的各边界张量等大时，整个 Pipeline 的传输字节数也增至 7/3 倍。论文 §2.2.2 用 v 倍描述通信量的增幅。在这个映射下，原有相邻 GPU 对上的传递次数恰好增至 v 倍，全链路统计还要算上连接 Chunk 的边界。

额外边界可能走节点内互联，也可能走跨节点网络。具体耗时还受张量大小、消息启动开销和与其他并行通信的带宽竞争影响。

交错调度何时更快：18 ms 的理论收益

令普通 Stage 的 tf + tb = 12 ms，仍取 p=4、m=8、v=2。普通 1F1B 的理想迭代耗时为 (8 + 3) × 12 = 132 ms，Interleaved 为 (8 + 1.5) × 12 = 114 ms。理论节省 18 ms。

Megatron Core：调度在源码中的位置

Megatron Core 0.18.0 由 get_forward_backward_func() 根据 PP/VPP 配置选择调度。普通 1F1B 与 Interleaved 分别由两个入口执行；后者用调度表关联 Microbatch 和 Model Chunk。P2PCommunicator 承担相邻 Pipeline Stage 之间的张量收发。

普通 1F1B 的直接收益是更早释放前向状态。Interleaved 节省了理想空闲时间，实际能否提高吞吐取决于这部分节省能覆盖多少新增关键路径开销。

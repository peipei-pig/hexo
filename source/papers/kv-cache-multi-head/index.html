全前缀重算与增量解码

模型并不是一次写出整句话，而是根据已经处理的 Token 预测下一个。每生成一个新 Token，模型仍要看历史；但看历史，不等于把历史的所有层重新计算一遍。这正是 KV Cache 要解决的问题。

用三个输入位置做一个可复算的对照：先把 The、␠cat 送入 Prefill，再把位置 3 的 ␠sat 送入 Decode，观察模型如何预测位置 4。这里的 ␠sat 是为了实验固定的第三个 Token，并不意味着模型一定会在 The cat 后生成它；␠ 表示前导空格。

位置 3 这一步，有两种计算方式：

因果掩码将位置 i 的可见范围限制在 1…i。只要前缀 token、位置编号和可见范围保持一致，追加位置 3 就不会改变位置 1、2 的输入表示。这个性质从词嵌入逐层传递，因此历史 K/V 可以原样复用。位置 3 的查询仍要计算自己对三个位置的注意力，浮点舍入可能让两条路径的结果略有差异。

要省的是历史位置的重复前向计算。新的 q₃ 仍需与 K₁、K₂、K₃ 匹配，并对 V₁、V₂、V₃ 加权。缓存没有取消注意力，而是让历史的 K/V 可以被再次读取。

Prefill 保存位置 1、2

Prefill 处理前两个位置：q₁ 看位置 1，q₂ 看位置 1、2。算完后，这一层留下两组 K/V；其他层也各自留下对应的 K/V。

位置 3 投影出 q₃、k₃、v₃

位置 3 的隐藏向量分别通过 Q/K/V 投影。Qwen2 再对 q₃、k₃ 应用位置 3 的 RoPE；v₃ 不做 RoPE。新的 K/V 此时已算出，但尚未写入这一层的缓存。

追加 K₃/V₃ 后计算当前注意力

把 K₃/V₃ 追加到该层缓存；当前 q₃ 与 K₁–K₃ 计算三个分数，Softmax 后加权 V₁–V₃，得到一个 Q 头的 z₃。旧位置的 q₁、q₂ 无需重新计算。

完成各层前向，得到位置 4 的 logits

当前层的各 Q 头输出拼接并投影，随后经过残差和 FFN 等运算；位置 3 的表示继续进入后续层。穿过全部 24 层、最终归一化和 LM head 后，得到用于预测位置 4 的 logits。预测出的 Token 尚未产生自己的 K/V。

请求结束，释放请求持有的缓存

演示在预测后结束。若没有跨请求前缀共享或缓存保留策略，该请求不再持有这些层的 KV；这不是每一步 Decode 都会发生的动作。

交互只画出一个 KV 头在一个注意力层内的状态；真实模型每层有自己的缓存，而且同一层可含多个 KV 头。点击“下一步”依次观察计算与缓存变化。

单头注意力计算

位置 3 并不会随身携带三个预制好的向量。它先形成当前层的隐藏表示，随后由三个不同的线性投影生成 Q、K、V。这里将送入投影的、已经经过该层输入 RMSNorm 的表示记为 x₃：对第 1 层，来源是词嵌入；对后续层，来源是上一层输出。Qwen2 对 Q、K 应用 RoPE，V 则直接来自 V 投影。

24 层前向与逐层缓存

前面只画了一层、一个 Q 头。真实的 Decode 要把位置 3 的隐藏状态依次送过 24 个 Transformer 层。每层都会重新产生属于该层的 Q₃/K₃/V₃，并读取该层自己的历史 KV。第 1 层的 K/V 不会拿去给第 2 层使用。

因此，KV Cache 不是一张覆盖全模型的 K/V 表，而是按层保存的多份状态。增量 Decode 仍须跑完全部 24 层；它省掉的，是每一层中对历史位置的重复前向计算。

单步 Decode 工作量

回到位置 3。假如不用缓存，模型会在每一层重新执行位置 1–3 的运算；有缓存时，只有位置 3 需要走完整的各层计算，而历史 K/V 从各自的缓存读取。

这一层的操作全前缀重算增量 Decode
历史位置 1、2 的 Q/K/V 投影重复执行省掉
历史位置 1、2 的注意力、FFN 等计算重复执行省掉
当前位置 3 的 Q/K/V、注意力与 FFN仍需执行仍需执行
q₃ 与 K₁–K₃ 打分、Softmax、V 加权仍需执行仍需执行
历史 K/V 的跨步保存与读取不持久保留需要存储、读取、追加

若只数单层、单个 Q 头的因果注意力中的有效 Query–Key 位置对，全前缀重算处理 1 + 2 + 3 = 6 对，增量 Decode 只处理位置 3 对三个 K 的 3 对。

令 T 为该 Decode 步包含新位置的总长度。全前缀重算需要 1 + 2 + … + T = T(T+1)/2 个可见位置对，增量 Decode 需要 T 个，差额 T(T−1)/2 来自历史查询。若从空缓存 Prefill P 个位置，则该步处理 P(P+1)/2 个可见位置对，并留下长度为 P 的缓存。

这些计数只描述因果掩码下有效的数学位置对，不是 GPU kernel 的实际乘法次数。真实延迟还取决于 Q/K/V 投影与 FFN、内核实现、调度开销、KV 的读写带宽、GQA 分组复用以及批大小。KV Cache 省去历史位置的前向计算，但不是让每步 Decode 的计算或访存变成常数。

MHA、GQA 与 MQA

标准多头注意力（MHA）为每个 Q 头配一组独立的 K/V 投影。每个头在同一个位置独立算出权重和输出，再由 WO 混合拼接结果。Transformer 原论文 §3.2.2

分组查询注意力（GQA）让组内的多个 Q 头读取同一组 K/V。多查询注意力（MQA）让所有 Q 头共享一组 K/V。两者都保留每个 Q 头各自的向量、注意力权重和输出。以均匀分组为例，每组包含 HQ/HKV 个 Q 头。GQA 论文 §2.2 · MQA 论文

这里的“共享”发生在同一层、同一个历史位置的 K/V 数据上，并非把多个 Q 头合并成一个头。Q 头仍然有 14 个，各自计算注意力分数和输出；因此不能把缓存减少到 1/7 直接解释为注意力计算量或端到端延迟也下降到 1/7。

        torch_dtype=torch.float32,
        attn_implementation="eager",
    ).cpu().eval()
    ids = torch.tensor([TOKEN_IDS], dtype=torch.long)

    with torch.inference_mode():
        full = model(input_ids=ids, use_cache=False,
                     output_attentions=True, return_dict=True)
        prefill = model(input_ids=ids[:, :2], use_cache=True,
                        output_attentions=True, return_dict=True)

        # Capture first layer's concatenated head outputs, before o_proj.
        captured = {}
        def save_attention_output(_module, inputs):
            captured["before_o_proj"] = inputs[0].detach().clone()
        handle = model.model.layers[0].self_attn.o_proj.register_forward_pre_hook(
            save_attention_output
        )
        try:
            step = model(input_ids=ids[:, 2:],
                         past_key_values=prefill.past_key_values,
                         use_cache=True, output_attentions=True, return_dict=True)
        finally:
            handle.remove()

    # Both paths predict position 4 after processing position 3.
    diff = (full.logits[:, -1, :] - step.logits[:, -1, :]).abs().max().item()
    head1 = step.attentions[0][0, 0, 0, :].tolist()  # [3] keys
    head1_full = full.attentions[0][0, 0, -1, :]
    attn_diff = (head1_full - step.attentions[0][0, 0, 0, :]).abs().max().item()
    z0 = captured["before_o_proj"][0, 0, 0].item()  # Q head 1, feature 0

    print("Cache length after Decode:", step.past_key_values.get_seq_length())
    print("Layer-1 first Q head weights:", [round(x, 6) for x in head1])
    print("Layer-1 first Q head output[0]:", round(z0, 6))
    print("Max attention-weight abs diff:", f"{attn_diff:.3g}")
    print("Max final-logits abs diff:", f"{diff:.3g}")
    print("Layer-1 attention shape in Decode:", tuple(step.attentions[0].shape))

KV 容量与读取量

单条序列每层保留 T 个位置，且层间 KV 配置相同时，逻辑 KV 数据量为：

M = T × L × HKV × (dK + dV) × b
L 为注意力层数，HKV 为每层 KV 头数，dK、dV 为每头维度，b 为每元素字节数

以 16 位缓存为例，Qwen2.5-0.5B 每增加一个位置，24 层合计新增 24 × 2 × (64 + 64) × 2 = 12,288 B，即 12 KiB。8,192 个位置占 96 MiB，32,768 个位置占 384 MiB。长度翻至 4 倍时，KV 数据量和单步每个 Q 头的可见位置数也都翻至 4 倍。

表中只改变 KV 头数，因此 GQA 的逻辑 KV 容量为假设 MHA 的 1/7。三种结构均有 14 个 Q 头，每层的可见 Q–K 位置对均为 14 × T。模型权重、质量和延迟需要在各自配置下另行比较。

对全因果 Decode，设每个独立的 K/V 元素只从 HBM 读一次，跨全部注意力层累计的逻辑读取数据量与上述 KV 数据量 M 同量级。它不是实际 HBM 流量的精确预测：GQA 中组内共享可以减少重复读取，实际内核也可能重新加载、使用片上缓存、执行动态拼接，或者采用量化与分页等布局。计算容量时还没有计入块尾空隙、量化元数据、分配开销以及多请求的共享关系。

长上下文的开销

KV Cache 把每步必须处理的历史位置，从“重新跑过网络”变成“读取已经保存的 K/V”。这是计算复用，而不是历史信息消失了。对于有 T 个可见位置的全因果 Decode，新的 Query 仍要访问对应的 K/V；随着上下文增长，缓存容量、读写量以及请求并发都会影响实际吞吐和延迟。

计算

旧位置的投影、注意力与 FFN 无需重算；当前位置仍需完成所有层。

容量

逻辑 KV 大小随 Token 数、层数和 KV 头数增长。

访存

长上下文 Decode 往往需要反复读取历史 K/V；GQA、分页和高效内核影响最终表现。

一条新 Token 的计算路径可以这样记住：进入当前层 → 生成 Q/K/V → 读本层历史 KV 并追加当前 KV → 当前 Q 聚合所有可见 V → 经输出投影、残差和 FFN 进入下一层 → 穿过全部层后得到下一 Token 的 logits。回到交互演示。

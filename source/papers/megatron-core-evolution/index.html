MoE 模型中的 Attention 与 Experts 虽然运行在同一批 GPU 上，却不一定适合相同的并行配置：Attention 可能需要张量并行与上下文并行，Experts 则可能更适合不同的专家并行和张量切分方式。0.10 引入的 MoE Parallel Folding，让两部分能够采用不同的逻辑并行映射。0.10 Release

0.10：MLA 扩展 Attention 内部的数据路径

0.12-0.13：数据流与流水线布局

MoE 让 Token 在专家之间流动，MTP 为训练增加未来 Token 的预测路径；模型结构不再规整，也让 Pipeline 的层分配更加重要。0.12 和 0.13 分别从通信、预测和布局三个方向扩展训练能力。

0.12：DeepEP 优化专家数据交换

MoE 的 Router 为每个 Token 选择专家。专家分布在不同设备时，Token 需要先被分发到目标专家，再将结果送回原位置。0.12 增加 DeepEP 支持，为细粒度 MoE 的 Dispatch / Combine 提供专门的通信路径。[5]

0.12：MTP 增加未来 Token 的训练信号

普通下一 Token 预测在当前位置学习预测下一个 Token；Multi-Token Prediction（MTP）在训练中增加对更远位置 Token 的预测路径，提供额外训练信号。0.12 发布说明列出 MTP 支持；它改变的是模型训练目标和计算路径，与 DeepEP 的专家通信作用于不同环节。[5]

实现关键一个 MTP 深度通常包含共享 Embedding、投影、Transformer Block 与共享输出头；不是单个线性分类器同时无条件预测所有未来 Token。
训练代价新增额外的 Forward/Backward、Activation、共享权重的重复调用和 MTP Loss；是否利于推理加速取决于额外的推理方案。
示意预测目标与因果深度链；MTP 输入对齐和共享头机制基于官方设计。不同版本对 CP、PP、特殊 Mask 的支持有差异。

与 DeepEP 的差异在于：MTP 不负责跨 GPU 传输，而是增加训练目标与预测模块。因此它首先影响模型末端的计算、Activation 和 Loss 组织；当 MTP 与 PP 组合时，还会产生额外的阶段负载。不要把训练时的多 Token 监督直接等同于推理阶段一次生成多个 Token。

MTP 增加了模型末端的计算和状态，因此部署到 Pipeline 时，需要关注预测模块的位置以及末端阶段的显存和工作量。0.13 发布时，MTP 与 Flexible Pipeline Layout 尚不兼容，相关组合需按版本核对。[6]

0.16：Optimizer State Offloading

历史边界：0.14 已出现面向 DeepSeek-V3 FP8 场景的 Optimizer Offloading；0.16 Release 进一步列出 Optimizer State Offloading。这里讨论的是能力扩展，不是 0.16 才首次想到把优化器状态放到 CPU。

Activation Offload 面向反向传播需要保存的中间结果；Optimizer State Offloading 则把优化器状态及 Master Weights 移向 CPU 内存。这些状态通常会跨整个训练 Step 持续存在，因此降低的是另一类常驻显存压力。0.16 官方发布说明明确列出这项支持。[9]

Activation 与 Optimizer State Offload 的区别
Activation Offload
Forward 激活→CPU 暂存→Backward 取回
关注激活峰值；成本是 D2H / H2D 与同步。
Optimizer State Offload
Adam Moments / Master→CPU 内存↔更新所需数据
关注优化器及 Master 状态；成本是更新路径和数据搬运。
重计算是“多算来省显存”，Offload 是“传输来省显存”；二者都可能降低有效吞吐，需要同时记录 GPU 峰值、CPU 内存、传输量与 Step Time。
两类 Offload 的开销

Activation Offload 主要影响前向保存与反向取回的临时激活；Optimizer State Offload 影响 Optimizer Step 的状态访问，通常在参数更新阶段对主机带宽、PCIe/NVLink 和 CPU 侧内存提出不同要求。

0.16：细粒度卸载与部分 CUDA Graph

显存与执行开销常常同时出现。0.16 发布说明列出细粒度 Activation Offloading，以及用于 EP Overlap 的 Partial CUDA Graph：前者针对部分激活管理内存，后者在选定范围使用 Graph，以减少相应 CPU 调度压力。两者各有适用条件，不能简单视为同一优化。[9]

两种机制需要分别验证显存、通信、同步和 Graph 的组合支持；实际效果以训练作业为准。

Packed Sequence 解决的是同一批次中如何组织不同长度的样本；Context Parallel（CP） 解决的是同一条长序列如何跨设备分布。对于 Attention，跨片依赖可以从 Q/K/V 的可见范围理解；对于 GDN 这类带状态递推的层，序列分片还必须保证状态依赖的正确性，因此不能直接套用 Attention 的通信逻辑。0.18 的代码变更中包含 GDN CP 实现。[11]

Checkpoint 跨布局恢复与状态类型有关；应分别验证支持范围和恢复后的训练行为。

分布式 Checkpoint 的重要性，不只是“保存成功”，而是能否正确恢复同一次训练：加载后的模型权重、优化器、随机数状态和数据进度都可能影响后续 Loss。对于混合层、GTP 或 FSDP v2 这些复杂布局，应分别验证同布局恢复与跨布局 Reshard，并区分权重可加载和 Bitwise Determinism 两个不同目标。

回看 0.8–0.20：模型、并行与训练状态

0.8 已经能够训练 MoE、Mamba Hybrid 和初步的多模态模型。后续变化并不是从 Dense 训练突然跨入混合模型，而是在既有分布式并行基础上，逐步适配不同模块的计算路径、并行域与数据表示。0.10 的 MoE Parallel Folding 是一个具体例子：Attention 与 Experts 可以使用不同的逻辑通信组，而不必共享完全一致的并行切分。[1][3]

模型结构逐渐复杂后，训练效率开始更多地受到数据搬运和执行顺序影响。DeepEP 处理专家间的 Token 往返，自定义 Pipeline Layout 调整层的放置；随后 A2A Overlap、HybridEP、Offload 和通信组抽象进一步改变通信、计算与显存的组织方式。它们都可能优化训练 Step 的一部分，但瓶颈不同，收益也取决于模型、负载与硬件拓扑。[5][7][8]

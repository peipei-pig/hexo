一句话总结：针对在线 LLM 服务中微批计算量不均造成的流水线气泡，论文用动态 prefill 分块和 decode 请求重平衡，在所测 PCIe 多 GPU 环境中提高满足延迟约束的服务能力。

论文：USENIX 官方页面 · 论文 PDF · 代码：Sys-KU/FastPP。

1. 背景：问题不是并行度，而是在线负载的不均衡

大模型参数和 KV cache 经常超过单卡显存。KV cache（键值缓存）保存已处理 token 的注意力键和值，使后续生成可以复用历史计算；prefill（预填充）处理输入提示并建立缓存，decode（解码）则利用缓存逐步生成输出 token。张量并行（tensor parallelism，TP）沿层内维度切分计算，让多张卡共同完成同一层；它能缩短单次计算，但每层都需要多 GPU 集体通信。互连带宽不足时，这些同步成为服务瓶颈。流水线并行（pipeline parallelism，PP）则沿模型深度切分层，将相邻阶段之间的中间激活传给下一张卡，通信模式与体量不同。

PP 并非免费收益。请求必须依次经过各阶段，而阶段之间只有同时存在多个微批（microbatch）时才能有效重叠。在线推理又不同于长度固定、批次规律的训练：请求随机到达，prompt 长度和输出长度不同，prefill 与 decode 会混合。一个阶段处理长 prefill 时，其他阶段可能先完成并等待，空闲时间就是流水线气泡。

论文 Figure 1 展示了未充分优化 PP 的反例：Qwen2.5-32B、Azure Conversation 和四张 PCIe A100 上，在较高请求率下 PP 的 P90 TTFT 低于 TP，但 PP 因流水线气泡导致 TPOT 更早触及约束；该图里 TP 可持续的请求率是 PP 的 1.2 倍。论文并没有证明“PP 总比 TP 快”，而是追问怎样降低 PP 独有的不平衡。

服务质量有两个互相牵制的目标：TTFT（time to first token）衡量请求到首 token 的等待，TPOT（time per output token）衡量后续 token 的生成间隔。加大 prefill 批量有利于清理等待队列，但过长的计算会拖慢正在解码的请求。本文的 goodput 特指定义为 P90 TTFT 与 P90 TPOT 均达标时的最高请求到达率，并非所有系统通用的 goodput 定义。

预备知识：分块与三种气泡

Chunked prefill 将长 prompt 拆成若干 token 块，与 decode 请求在不同迭代混合执行。小块限制一次 prefill 对其他微批的阻塞；但块太小会降低一次批处理的计算效率并抬高排队时间。块大小因此是一个与负载共同变化的控制量，而不是越小越好。

论文 Figure 2 将失衡分成三类：P-P 是两个 prefill 微批长度不同；P-D 是 prefill 与 decode 的计算量不同；D-D 是两个 decode 微批所含请求数量不同。前两类可通过限制 prefill 工作量缓解；第三类即使没有 prefill 也会持续出现，因此需要另外的重平衡机制。

2. 方法：让分块大小随系统状态变化

2.1 优化目标与控制信号

两种分块策略遵循同一原则：在系统能处理当前请求负载、并尽量满足 TPOT 约束的前提下，优先使用较小块以减轻气泡。若块太小，prefill 吞吐跟不上到达流量，队列累积，TTFT 变差；若块太大，较慢的 prefill 迭代可能阻塞其他微批，TPOT 变差。

理解反馈控制可把 slack 写成下式，其中 $S$ 是对应 SLO，$L$ 是观测延迟；正值表示还有余量，负值表示已经超标。这个式子用于解释文中的 slack，不能理解为运行时必然逐请求精确测量。

$$s_{\mathrm{TTFT}}=S_{\mathrm{TTFT}}-L_{\mathrm{TTFT}},\qquad s_{\mathrm{TPOT}}=S_{\mathrm{TPOT}}-L_{\mathrm{TPOT}}.$$

人话：首 token 余量变小意味着队列压力上升；输出 token 余量变小意味着当前 decode 受阻的风险上升。

2.2 贪心策略：用反馈逐步调整

论文 Algorithm 1 将候选块限制在离散集合 $\mathcal C$，例如以 128 token 为步长。初始值取最小块，更新间隔为流水线深度 $D_p$ 个调度迭代：一个微批走完整条流水线之前，块大小变化的效果尚不能完整显现。

第一优先级是内存。若空闲 KV cache 比例低于水位，算法把块重置到大于当前运行请求数的最小候选值，优先推进在途请求并回收缓存。这是降低内存压力的启发式，不构成任意条件下避免 OOM 的形式化保证。

内存充足时，若 TPOT 已超标或 TTFT 余量很大，就减小块；若 TTFT 余量紧张而 TPOT 仍有充足余量，则增大块。将论文中的条件概括如下；$\delta$ 是步长，$\alpha,\beta,\gamma$ 是阈值，集合边界处需要截断：

$$c_{t+1}=\begin{cases}c_t-\delta,&s_{\mathrm{TPOT}}<0\ \text{或}\ s_{\mathrm{TTFT}}>\alpha S_{\mathrm{TTFT}},\\c_t+\delta,&s_{\mathrm{TTFT}}<\beta S_{\mathrm{TTFT}}\ \text{且}\ s_{\mathrm{TPOT}}>\gamma S_{\mathrm{TPOT}},\\c_t,&\text{其他情况。}\end{cases}$$

人话：decode 有危险或请求较少时缩小块；只有队列有压力且 decode 留有余量时才扩大块。KV 低水位检查优先于此式。

论文作者明确指出贪心法的局限：它只看过去的指标，且每次只改变一个步长；流水线反馈有延迟，其他阶段的大块还会污染延迟信号。流量突变时，控制器可能一直在追赶变化中的合适值。实现中的具体阈值和保护逻辑比论文伪代码更细，不应混为完全相同。

2.3 预测策略：先估算，再选择最小可行块

预测式动态分块（DCPpred）将等待队列、运行中批次、KV 空间和近期到达率作为系统状态，对每个候选块预测迭代延迟与吞吐量。它把服务要求转化为两个方向相反的约束：TPOT 提供块大小的上限，处理到达请求与积压所需的 prefill 吞吐提供下限。

延迟预测器 ALP 将一次迭代的时间拆为离线和在线两部分：

$$T_{\mathrm{iter}}=T_{\mathrm{offline}}+T_{\mathrm{online}},\qquad T_{\mathrm{offline}}=\alpha_0 N_{\mathrm{tokens}}+\alpha_1.$$

人话：大头线性层成本主要由本次 token 数 $N_{\mathrm{tokens}}$ 决定，可先在目标硬件上离线测量；$\alpha_0,\alpha_1$ 是拟合系数。原文在 128–2048 token 范围做离线测量，实际硬件上有离散台阶，不应把这个线性近似视作普适物理定律。

注意力开销随上下文和请求构成变化，因此论文用三个特征估计在线分量：

$$T_{\mathrm{online}}=\beta_0\sum (L_{\mathrm{past}}L_{\mathrm{pre}})+\beta_1\sum L_{\mathrm{pre}}^2+\beta_2\sum L_{\mathrm{dec}}+\epsilon.$$

人话：第一项是新 prefill 块与已有上下文之间的注意力，第二项是当前块内部注意力，第三项是 decode 访问历史上下文；求和覆盖相应批内请求。$L_{\mathrm{past}}$ 是历史前缀长度，$L_{\mathrm{pre}}$ 是当前块长度，$L_{\mathrm{dec}}$ 是解码请求上下文长度，$\epsilon$ 表示残差或噪声。

每次迭代把实测延迟与离线预测的差额作为反馈，使用递归最小二乘（RLS）在线调整注意力系数。RLS 的协方差矩阵有助于处理平方项与线性项量级差异；遗忘因子提高近期观测的权重。预测器并非消除误差，而是在轻量和可适应性之间取舍。

预测分块：四步流程

1 · 读取状态等待队列、运行批次、KV 剩余和近期请求速率
2 · 预测候选对每个块预测流水线循环延迟和 prefill 吞吐
3 · 同时筛选延迟不得超过 TPOT 上限；吞吐须覆盖负载
4 · 选择并反馈取最小可行块；执行后用实测延迟更新模型

Figure 6 给出选择流程。图中预测吞吐下界排除了 128 和 256；预测延迟上界排除了 640 等较大的候选，384 和 512 均位于可行范围，故选择更小的 384。图中的界限和数字是论文的流程示例；下方另有一组自造数字供练习。对块 $c$，用 $D_p\hat T_{\mathrm{iter}}(c)$ 近似该微批完成一轮流水线的延迟；其中 $D_p$ 为阶段数，$\hat T_{\mathrm{iter}}$ 为预测的单阶段迭代时间。该乘法是调度近似，不是整个请求从到达到最后一个 token 的端到端完成时间；真实延迟也受其他微批及阶段波动影响。记 $\hat R(c)$ 为预测 prefill 吞吐，$R_{\min}$ 为处理到达流量及老化积压所需的吞吐，可将选择原则概括为：

$$c^*=\min\{c\in\mathcal C: D_p\hat T_{\mathrm{iter}}(c)\le S_{\mathrm{TPOT}},\quad \hat R(c)\ge R_{\min}\}.$$

人话：先排除预计伤害 TPOT 的大块，再从能跟上需求的候选中选最小块。这是按论文文字归纳的优化表达式，并非作者声称的全局最优证明。

所需吞吐包含滑动窗口中估计的到达 token 速率，以及临近 TTFT 期限的等待请求的追赶需求；后者大致按其待处理 prompt token 数除以剩余预算估计。若两类条件无法同时满足，论文选择仍满足 TPOT 的最大候选，以尽力排空队列；若连最小块也不能满足 TPOT，源码返回最小候选作为退化处理，不能保证 SLO。

2.4 Delay scheduling：主动暂缓一部分 decode

动态 prefill 块不能直接解决纯 decode 迭代中的 D-D 失衡。论文 §4.2 依据硬件执行时间对 token 数的台阶状变化调整微批：例如 Figure 3c 所示，129 token 的线性层成本与 256 token 接近，略微超过边界却会让该微批明显拖慢其他阶段。

当批量只比硬件效率边界大一点时，系统可暂缓超出的请求，让批次回落到边界；若超出更多，则朝各微批平均请求数重平衡，必要时恢复先前暂缓的请求。Figure 7 的示例显示，暂缓 E、F 后，其他微批可以更均匀地前进，等空位出现再恢复。这里的“迁移”主要是调度批次的请求重组，不应无条件理解成把整份 KV cache 从一张 GPU 复制到另一张 GPU。

请求选择体现不同延迟指标的权衡：TPOT 余量不足时，论文优先暂缓较老请求以保护较新请求；余量充足时优先暂缓较新请求，让较老请求更快结束并释放 KV 内存。暂缓会增加被选请求的 token 间隔，因此更好的总体完成时间不意味着每个请求都受益。

示例 3：把多出的 decode 请求暂缓一轮

假设两个微批分别有 130 和 100 个 decode 请求，硬件高效边界为 128。若多出的 2 个请求处在策略允许的暂缓阈值内，调度器可先将较大的微批降到 128；当另一个微批出现空位时再恢复这 2 个请求。示例中的阈值和批量仅用于解释，不是论文对所有硬件的默认保证。

原文摘录： “the primary objective is to minimize pipeline bubbles” (§4.1)；“the smallest feasible chunk size” (§4.1.2)；“temporarily preempt the excess requests” (§4.2)。这些短语分别概括目标、候选选择和 decode 控制手段。

4. 实验：看清基线、负载与指标

环境为四张 NVIDIA A100 40GB，GPU 经 PCIe 4.0 连接主机；CPU 为 128 核 AMD EPYC 9754、内存 768 GB。模型为 BF16 Qwen2.5-32B 与 14B；框架为 SGLang 0.4.1、PyTorch 2.5.1、CUDA 12.4。到达率扫描使用泊松到达；另有 Azure 真实时间轨迹回放。原文 Figure 8 的 Azure、ShareGPT、CNN 平均输入/输出 token 长度分别为 1161/212、226/199、883/65；CNN-Reversed 交换输入与输出分布以构造 decode-heavy 条件。

主要 SLO 为 P90 TTFT 不超过 2000 ms 且 P90 TPOT 不超过 200 ms。TP 使用 2048 token 默认块；PP 同时比较多个静态块，其中 PPstatic 指按对应负载离线选出 goodput 最高的静态块。这个基线经过调优，因而与默认 2048 块不同。动态策略的主要收益既可能是 goodput，也可能是在 goodput 已接近时改善延迟。

4.3 真实轨迹、严格 SLO 与公平性

Figure 14 将 AzureConv 前 15 分钟按 0.9 倍原始到达率回放，选择该缩放使调优静态 PP 的达标率约为 90%。TP、默认 PP2048、调优 PPstatic 的双 SLO 达标率分别为 1.9%、1.6%、92.5%；贪心、预测、预测加 DS 分别为 93.5%、94.5%、94.6%。这是逐请求双 SLO 达标比例，与 Figure 9 使用的 P90 约束下最高请求率不是同一指标，也不是同一实验设置。

Figure 12 显示更严约束可能使方案失效：32B、SLO 缩放 0.2 时，最小候选块都不能满足 TPOT，所有 PP 类方案 goodput 为零。Figure 13 的合成 decode-heavy 场景中，DS 相对预测 DCP 平均与 P99 E2E 分别减少 4062 ms 和 8088 ms，但被暂缓请求使 P99 TPOT 恶化 15%。因此，调度器优化总体指标时应同时监测被牺牲请求的尾部体验。

5. 局限与适用边界

作者明确指出的限制：贪心控制是反应式、逐步调整并受到流水线反馈延迟影响；极严格 SLO 下最小块也可能不可行；decode-heavy 时 DCP 可控空间有限；DS 虽改善完成时间，可能恶化被暂缓请求的尾部 TPOT。作者还观察到 DS 在严格 SLO 下可能因未积累足够请求而达不到激活阈值。

独立判断：实验集中在单节点四张 PCIe A100 和两个同系列稠密 Qwen 模型，尚不能外推到 NVLink、高速跨节点网络、不同 GPU/NPU、MoE 或异构阶段。TP 的通信成本与 PP 气泡都随拓扑、并行度和内核变化；尤其 Figure 1 的普通 PP 已展示反例。真实轨迹仅报告一个缩放比例和窗口，真实突发、超长上下文、取消请求、混部干扰与多租户公平性仍需更广泛验证。

此外，预测器对滑动窗口到达率和历史特征变化的适应能力可能受突发分布漂移影响；论文提供的 MAPE 是指定 Azure 工作负载上的结果，不能替代在新环境下的重新 profiling 与端到端测试。固定 SLO 下的 P90 目标也可能掩盖少数请求更严重的饥饿，应同时检查 P99、最大等待时间、逐请求达标比例及 KV 占用。

部署时可先在目标拓扑上测 TP 与多种静态 PP 块，确认瓶颈来自通信还是气泡；再分别开启动态块与重平衡，按 prefill-heavy、decode-heavy 和真实到达轨迹测量。最好报告每种方案的吞吐、TTFT/TPOT 分位数、端到端延迟、KV 使用率及尾部公平性，同时固定模型、精度、缓存和基线参数。

6. 结论

论文的贡献是把在线 PP 气泡拆解为可观察的工作量失衡，并分别用基于 SLO 的动态 prefill 分块与 decode 微批重平衡处理。实验中，针对 PCIe 环境经过调优的 PP 已显著优于默认 TP；动态策略进一步改善延迟，DS 则在 decode-heavy 条件下提供明显额外收益。方法的可迁移价值在于控制思路，具体收益仍取决于拓扑、模型、负载与 SLO。
